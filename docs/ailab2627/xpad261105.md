在 Pad 的 ZeroTermux 终端中（或者在 PC 个人电脑 ssh 登录 Pad 的界面中，下同）执行以下命令，安装 ollama：

```bash
ollama
```

```bash
ollama serve &
```

## 三、大模型推理性能测试与分析

**实验目的**

理解大模型推理过程中的计算开销，掌握推理性能的基本测量方法，认识计算资源对模型运行的影响。

**实验任务**

可以设置多个不同的测试条件，比如，<u>冷启动请求（卸载模型后重新调用）、热启动请求（保持模型驻留，重复调用）短文本提问、长文本提问</u>等，测试<u>首 Token 延迟、总响应时间、输入/输出Token数、生成吞吐量、内存占用</u>等指标。每项测试至少重复三次，记录原始结果，并计算平均值。测试时尽可能保持设备运行状态一致，避免其他高负载任务干扰。

| 实验任务 | 控制变量 | 测量或分析指标 |
| ---- | ---- | ---- |
| 任务A：冷启动与热启动性能比较 | 相同模型、提示词及生成参数 | 加载时间、总耗时、输出吞吐量等 |
| 任务B：不同输入长度下的性能比较 | 相同模型、生成长度上限等 | 输入 Token 数、输入处理耗时、总耗时等 |
| 任务C：不同输出长度下的性能比较 | 相同模型、输入及其他参数 | 输出 Token 数、总耗时、输出吞吐量等 |
| 任务D：内存占用分析 | 相同设备及模型 | 加载前后可用内存、推理过程中的内存变化等 |


**关于指标**

- 首 Token 延迟（Time to First Token，TTFT）：从客户端发出请求到收到第一个非空生成内容片段之间的时间。实验中通过流式 API 进行测量。该指标反映客户端可感知的首次输出等待时间，可能包含模型加载、输入处理、输出生成及通信开销。
- 总响应时间：从客户端发出请求到接收完模型生成的全部响应内容之间的时间，单位为秒（s）。该指标反映用户完成一次完整问答所需的等待时间，通常包含模型加载、输入处理、输出生成及通信等环节的耗时，可用于衡量模型推理服务的端到端响应性能。
- 生成吞吐量（Output Token Throughput）：模型在输出生成阶段平均每秒生成的 Token 数量，单位为 Token/s。该指标用于衡量模型的输出生成速度，不等同于包含模型加载、输入处理等阶段的端到端处理速度。

<u>提示1</u>：Ollama 的 `/api/generate` 接口能够返回 `load_duration`（模型加载耗时）、`total_duration`（服务端处理一次生成请求的总耗时）、`eval_count`（输出 Token 数量）、`eval_duration`（输出生成耗时）等性能指标。上述时间指标的单位均为纳秒（ns），可用于分析模型推理性能。其中，`total_duration` 是服务端统计的耗时，与客户端实际测得的端到端总响应时间可能存在差异。

例如，执行以下命令（⚠️确保 `ollama serve &` 在运行。如未运行，建议新启窗口运行。）

```bash
curl -s http://127.0.0.1:11434/api/generate \
  -H "Content-Type: application/json" \
  -d '{
    "model": "EntropyYue/chatglm3",
    "prompt": "请简要解释什么是大语言模型推理。",
    "stream": false,
    "keep_alive": "5m",
    "options": {
      "num_predict": 128
    }
  }'
```

可观察返回结果中的 `total_duration`、`load_duration`、`prompt_eval_count`、`prompt_eval_duration`、`eval_count` 和 `eval_duration` 等字段，记录数据并计算吞吐量。请求地址需要根据设备的实际情况填写。

首 Token 延迟需要使用流式 API 进行测量。设置 `"stream": true`，并通过客户端计时程序记录请求发起时刻和收到第一个非空生成内容片段的时刻。设置 `"stream": false` 时，适合获取完整响应及性能统计数据，但不能直接测量首 Token 延迟。需要说明的是，单纯改成 `"stream": true` 也不意味着终端会自动显示 TTFT 数值；仍需要使用计时程序。


<!-- $$生成吞吐量 = \frac{\text{eval_count}}{\text{eval_duration} / 10^9} \text{token\/s}$$ -->
<!-- $$生成吞吐量 = \frac{\text{eval_count}}{text{eval_duration} / 10^9} \text{token\/s}$$ -->
```text
生成吞吐量 = eval_count / eval_duration * 10^9
```

其中：

* `eval_count`：模型生成的 Token 数量，单位为 Token。
* `eval_duration`：生成这些 Token 所花费的时间，单位为纳秒（ns）。
* 10^9（10的9次方）：将纳秒转换为秒的换算系数。

大模型推理包含输入处理（Prefill）和输出生成（Decode）两个主要计算阶段，所以吞吐量不只有生成吞吐量，还有输入处理吞吐量。

<!-- $$输入处理吞吐量 = \frac{\text{prompt\_eval\_count}}{\text{prompt\_eval\_duration} / 10^9} \text{ token/s}$$ -->
<!-- $$输入处理吞吐量 = \frac{\text{prompt_eval_count}}{\text{prompt_eval_duration} / 10^9} \text{ token/s}$$ -->

```text
输入处理吞吐量 = prompt_eval_count / prompt_eval_duration * 10^9
```

其中：

* `prompt_eval_count`：输入提示词的 Token 数量。
* `prompt_eval_duration`：输入处理阶段的耗时，单位为纳秒。
* 10^9（10的9次方）：将纳秒转换为秒的换算系数。

注意：输入处理吞吐量的计算可能受到提示词缓存的影响。为保证不同实验之间具有可比性，应尽量控制输入缓存条件，并记录缓存命中情况。对于存在明显缓存命中的请求，不宜直接将全部输入 Token 数与未缓存部分的处理耗时相除，并将结果解释为纯粹的输入计算速度。

<u>提示2</u>：对于 Android + Termux 环境，可使用模型加载前后的系统可用内存变化作为基础观察指标，用 free -h 记录相关数据；也可以使用 top 观察进程资源使用情况。

<u>提示3</u>：关于“卸载模型后重新调用”

```bash
# 卸载当前已加载的模型
ollama stop EntropyYue/chatglm3

# 查看当前正在运行的模型
ollama ps
```

## 大模型推理参数对生成效果的影响

### 实验目的

理解大语言模型生成机制中的关键参数，掌握通过参数配置调整模型输出的方法。

### 实验任务

选择一个已部署的模型，研究以下参数：

| 实验任务 | 实验设置示例 | 观察指标 |
| ---- | ---- | ---- |
| 任务A：Temperature | 0.1、0.5、1.0 | 内容多样性 |
| 任务B：Top-p | 0.5、0.9 | 内容多样性 |
| 任务C：num_ctx | 1024、2048、4096 | 长文本信息利用能力 |
| 任务D：num_predict | 64、128、256 | 输出长度 |

这些参数均可以通过 Ollama 的配置机制设置，具体取值应结合实际设备、模型支持情况、请求长度、上下文长度调整。例如，

```bash
curl -s http://127.0.0.1:11434/api/generate \
-H "Content-Type: application/json" \
-d '{
    "model": "llama2:7b",
    "prompt": "请简要介绍大语言模型。",
    "stream": false,
    "options": {
    "temperature": 0.5,
    "top_p": 0.9,
    "num_ctx": 2048,
    "num_predict": 128
    }
}'
```

说明：

- 每次只改变一个参数，其他参数和输入保持一致。
- 相同设置下进行重复测试，避免将随机输出差异误认为参数的确定性效果。
- 可提交：参数配置表、典型输出对比、结果分析。

一般来说：

- Temperature 控制内容的发散程度。低温度（0.1）格式固着严重、容易复读；高温度（1.0）创意增加，但容易产生幻觉和偏离格式。
- Top-p 控制词表候选池大小。在相同温度下，较低的 Top-p 更保守，较高的 Top-p 词汇更丰富，但也容易引入不合理的内容。
- num_ctx 决定了模型能处理多长的输入。当输入长度超过窗口时，开头的关键信息会被静默截断，导致模型产生事实性幻觉（如瞎编负责人名字）。
- num_predict 是生成内容的物理天花板。模型本身缺乏“字数控制”能力，必须依赖此参数强制截断，但这会损害文本的完整性。想要模型自然结束，需要给它足够大的数值（如 512 以上），或者通过 stop 参数设定停止词。

### 任务C：不同上下文窗口设置对长文本信息利用效果的影响。

`num_ctx` 用于设置模型生成下一个 Token 时能够利用的上下文窗口大小。

准备一段具有一定长度的课程介绍文本，在材料开头、中间和结尾分别放置明确、可验证的信息，例如课程负责人、实验项目编号、实验提交日期等。分别设置 `num_ctx` 为 1024、2048 和 4096，在其他生成参数保持一致的条件下进行测试。

```text
课程负责人：张老师；实验项目编号：A17  # 材料开头

……较长的课程介绍文本……

教学目标、课程安排、实验要求……  # 扩充为较长文本

最终实验提交日期：第16教学周  # 材料结尾
```

然后依次提问：

- 课程负责人是谁？
- 实验项目编号是什么？ 
- 最终实验提交日期是什么？

**实验要求**

1. 测试材料应具有足够的长度，使其能够触及较小上下文窗口的限制。
2. 记录实际输入 Token 数量，并注意提示词模板及输出生成也会占用上下文窗口。
3. 分别提问材料开头、中间和结尾的信息，记录模型回答是否正确。
4. 每组重复测试至少三次，比较不同上下文窗口设置下模型的信息提取情况。


### 任务D：最大生成长度对响应时间和文本完整性的影响

num_predict 控制模型最多生成多少个 Token。

```text
请介绍大语言模型推理过程中的主要计算步骤，要求分条说明，并给出尽可能完整的解释。
```

**观察**

- 实际生成 Token 数量。
- 响应是否在达到 Token 上限前结束。
- 总响应时间。
- 输出是否出现内容截断。
